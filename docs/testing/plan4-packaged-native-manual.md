# Ручной native-UI прогон приёмки Plan 4

Статус этого сценария: **NOT RUN** до фактического выполнения всех шести
шагов на текущем packaged app.

## Перед началом

Codex самостоятельно подготовит синтетический workspace и inbox-файлы, соберёт
приложение, проверит хеши артефактов, создаст резервную копию профиля и запустит
точный packaged app. Codex также сообщит точные динамические пути и значения,
которые нужны для UI-прогона. Не начинайте, пока Codex явно не сообщит, что всё
готово.

Техническая предпроверка выполняется только Codex; её подробное описание
находится в [manager-only preflight](plan4-packaged-native-preflight.md) и не
является инструкцией оператору. Не устанавливайте и не используйте CuaDriver:
оператор выполняет только обычное видимое взаимодействие с macOS.

## 1. Workspace, inbox и выбранное состояние

### Действие

В `Settings` через native file pickers выберите подготовленный workspace,
затем выберите подготовленные inbox для MyNetDiary и Hevy через `Choose inbox`.
Подтвердите, что выбранный provider и его выбранный state отображаются явно.

### Ожидаемый результат

`Settings` показывает именно подготовленный workspace и оба выбранных inbox.
Выбранные provider и state видимы, а посторонние расположения и содержимое
источников не отображаются.

### Если не получилось

Остановите UI-прогон и сообщите Codex точные видимые labels, state и сообщение
file picker. Не переходите к следующему шагу и не заменяйте native picker другим
способом выбора.

## 2. Refresh без перезапуска

### Действие

Вернитесь в `Overview`, один раз нажмите `Refresh data` и дождитесь окончания
операции. Не перезапускайте приложение.

### Ожидаемый результат

Во время операции виден `Refreshing data…`, затем тот же процесс показывает
`Healthy`, `0 active jobs` и `0 attention items`. Импортированные synthetic data
становятся видимыми в dashboard без перезапуска приложения.

### Если не получилось

Остановите этот шаг и сообщите Codex, какой state, счётчик или видимый элемент
изменился неправильно. Зафиксируйте только безопасный синтетический экран; не
переходите к техническим проверкам.

## 3. Идемпотентность текущей ошибки

### Действие

Начинайте только после того, как Codex сообщит, что failure fixture подготовлена.
Нажимайте `Refresh data` повторно ровно так, как указал Codex, не изменяя
fixture. В `Sources & quality` визуально проверьте текущий error/attention item и
доступность `Retry import` или применимого `Open settings`.

### Ожидаемый результат

Статус отображается как `Attention` или другое точное typed import-error state.
Текущий attention/error count остаётся одним и не превращается в накопительные
дубликаты после повторных Refresh. Причина остаётся понятной и privacy-safe, а
`Retry import` представляет доступное действие для текущего item.

### Если не получилось

Остановите повторные действия и сообщите Codex количество до и после, точный
видимый state и доступные действия. Не создавайте дополнительные refresh-прогоны
в обход указаний Codex.

## 4. Все страницы Analytics

### Действие

Откройте и визуально осмотрите каждую страницу Analytics: `Overview`, `Body`,
`Nutrition`, `Activity`, `Strength`, `Sources & quality`, `Phase events` и
`Settings`. Проверьте cards, charts, gaps, provider view и source-quality view.

### Ожидаемый результат

Каждая страница имеет ожидаемый title и availability state; cards и charts
отображаются, а недостаточные или отсутствующие данные представлены явными gaps,
а не выдуманными нулевыми значениями. Provider, module states, retry surface и
source-quality information видимы там, где они применимы. Raw payloads, source
paths и private data не отображаются.

### Если не получилось

Сообщите Codex страницу, на которой возникла проблема, и точный видимый
симптом. При необходимости приложите только synthetic-only screenshot без
личных данных, исходных экспортов и приватных путей.

## 5. Phase event: создание, редактирование и удаление

### Действие

В `Phase events` создайте synthetic event типа `cut` с датами `2026-01-15` —
`2026-01-16`, описанием `synthetic phase` и включённым `Exclude from TDEE`.
Сохраните event, измените его описание на `synthetic phase edited` и сохраните
изменение. Проверьте overlay/state, затем откройте подтверждение удаления,
сначала отмените его и убедитесь, что event остался, после чего явно подтвердите
удаление и проверьте, что event исчез.

### Ожидаемый результат

Созданный event появляется без перезапуска. Изменённое описание сохраняется,
phase overlay и состояние исключённых из TDEE дней обновляются, отмена удаления
сохраняет event, а подтверждённое удаление убирает его из списка.

### Если не получилось

Остановите этот шаг и сообщите Codex, на какой операции — create, edit, cancel
или delete — возникла проблема, вместе с точным видимым state. Приложите
screenshot только если он synthetic-only и необходим для разбора.

## 6. Нормальный выход и отчёт

### Действие

Завершите приложение обычным видимым application quit control. После этого
сообщите Codex результат каждого из шести шагов и любую обнаруженную видимую
или функциональную проблему. Если для объяснения проблемы нужен screenshot,
приложите только synthetic-only screenshot.

### Ожидаемый результат

Приложение завершается нормально. Отчёт содержит только результаты native-UI
проверок, безопасные синтетические значения и, при необходимости, безопасные
скриншоты; никаких реальных exports, private records или личных данных.

### Если не получилось

Сообщите Codex точное видимое поведение и последний завершённый шаг. Не пытайтесь
исправлять проблему техническими командами или сторонним UI-контроллером; статус
приёмки остаётся `NOT RUN`, пока результат не будет отдельно рассмотрен.

До фактического завершения и фиксации всех шести шагов общий статус этого
сценария остаётся **NOT RUN**.
